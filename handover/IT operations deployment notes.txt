Before pushing this release to Render
1. Preserve a recovery copy of the existing database and keep normal app traffic away while applying the payroll data migration. Existing pre-encryption archives and logs do not become encrypted retroactively.
2. Install the updated requirements, including cryptography.
3. Generate a unique payroll key with the installed cryptography library:
   python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
   Store this secret in approved secret storage. Set SALARY_ENCRYPTION_KEYS in the web and worker environments. Never use the test key in settings_test.py. The first comma-separated key encrypts new records; later keys read older data and archives. Preserve these keys independently of database backups.
4. Payroll migration 0037 checks the key before changing existing finance tables. Migration 0038 encrypts existing salaries and redacts salary audit values; it is intentionally irreversible through ordinary migration rollback. Migration 0040 adds checks rejecting plaintext Salary writes. Drain old application writers before the backfill and deploy the new code together.
5. Render's checked-in build command already runs migrate. Configure the secret before pushing; do not run migrations casually against the production DATABASE_URL from this workstation.

Use the existing SMTP configuration: EMAIL_HOST, EMAIL_PORT, EMAIL_HOST_USER, EMAIL_HOST_PASSWORD, DEFAULT_FROM_EMAIL and TLS settings. Console/dummy email backends cannot count as offsite backup delivery. Local test-mail capture is allowed only by explicit debug/test settings. Mail-server acceptance is not proof that an inbox received the message; verify the actual backup mailboxes and their retention policy in staging.

An administrator assigns role IT. In IT Operations > Backups & Schedules choose recipients who have active accounts and valid email addresses, save the schedule, and run a manual backup. Recover the ZIP from the actual mailbox and test restoring it to an approved staging database before scheduling production jobs.

Scheduler
Run a separate worker with the same database and secrets as the web app:
   python manage.py run_backup_jobs --loop
It polls every 30 seconds. Alternatively invoke this command without --loop from the host scheduler once per minute:
   python manage.py run_backup_jobs
The schedule is managed in IT Operations > Backups & Schedules. Backup history and heartbeat metadata are shared through the database, so a separate worker need not share the web app's temporary disk. The database payload is staged only for email packaging and removed after successful send by default. File-level operation locks prevent overlap within one staging directory. Stop other workers and drain other web instances before a restore.

PostgreSQL prerequisites
Install compatible pg_dump and pg_restore client utilities in both web and worker runtimes. PG_DUMP_BIN and PG_RESTORE_BIN can point to their executable paths. The app invokes argument lists without a shell; the password is supplied through the subprocess environment. Restore uses a transaction and exits on the first error. Run a PostgreSQL staging recovery, verify its indexes/constraints and confirm the operation fits hosting request time limits before exposing restore in production. Restore only trusted archives generated by this application; PostgreSQL restore executes the archived database's commands.
Reference: https://www.postgresql.org/docs/current/app-pgrestore.html

Restore procedure
1. Stop normal traffic and competing workers. DB_MAINTENANCE_MODE is an operator gate; it does not drain hosting traffic for you.
2. Temporarily set DB_RESTORE_ENABLED=True and DB_MAINTENANCE_MODE=True.
3. Import the trusted recovery ZIP from a backup email in IT Operations.
4. Verify the selected snapshot and type RESTORE followed by its ID; confirm the current operator password.
5. A fresh safety archive must be emailed successfully before the restore starts. Failure to send it stops the restore.
6. After restore, all sessions are invalidated and schedules are disabled. Sign in with an account that exists in the selected snapshot, verify data and salary totals, then re-enable the schedule intentionally.
7. Restore and maintenance flags should be turned off when recovery is complete.
For a replacement database, DB_RESTORE_ALLOW_DIFFERENT_DATABASE=True is an additional explicit operator override. The engine, application migration version and required payroll keys must still match.

Restore archives contain checksums, migration identifiers and payroll-key fingerprints, not the payroll keys. A checksum is an integrity check, not proof that an untrusted archive is safe. Keep the application SECRET_KEY and payroll keys in independent secret recovery storage. Old keys are needed for old encrypted archives; losing them makes the payroll unreadable.
Reference: https://cryptography.io/en/latest/fernet/

Storage and operational limits
Email attachments are limited to the configured size; oversized captures fail explicitly. Database backups do not contain media/Blob objects, which need their own recovery policy. Only metadata and supplementary audit logs stay on the application host by default; successful database payloads are removed. If a worker crashes and leaves a .operation.lock file, verify that no backup/restore process is running before removing that exact lock file. Do not disable the lock while an operation is active.

Security scope
Primary Admin and Financial Admin roles may mutate individual salary records; another role's superuser flag alone does not grant payroll access. UI/API/export salary pools retain only totals. Role changes made through model saves and normal queryset privilege updates are audited; forged account-role requests are denied and generate security events. Database administrators issuing arbitrary SQL outside the application require separate database audit controls. A person with both the database and the payroll key can decrypt individual values; application masking cannot protect against control of the application runtime and its secrets.

Salary SQL columns intentionally contain zero placeholders. Use the supported app calculations for payroll totals; do not sum the masked columns in an external report. Protected plaintext is also validated before encryption so masking cannot bypass numeric field limits.

Salary key migration checklist
- Preserve the exact SALARY_ENCRYPTION_KEYS list, including old keys and ordering. Do not generate a replacement for an existing database.
- Name authorised custodians. Store the key list in an approved secret manager and an independent encrypted recovery copy; keep database archives and keys separate.
- Transfer keys through the secret manager or a restricted encrypted channel. Configure identical values on destination web and backup workers before migrations or recovery. Never put keys in source control, email, recovery ZIPs, screenshots or this handover.
- Rehearse migration to the matching app release. Compare salary totals through the app, check access restrictions and validate emailed recovery attachments. Missing keys must fail closed.
- Record vault references and verification dates, never key values. Remove temporary copies, revoke retired host access and retain historical keys needed by retained data/archives. Key rotation is a separate controlled activity; adding a key does not backfill ciphertext.

Backup SMTP warnings
Migration 0041 adds persistent backup-email health metadata. IT pages and the enabled backup worker inspect configuration without sending test email. Missing settings and failed sends notify active IT/admin users in the in-app bell, not via the broken SMTP channel. A matching warning state is deduplicated across workers/page refreshes. Corrected settings become unverified until a send succeeds. Actual send failure remains visible until success. Restart affected services after environment changes, run a backup, verify mail-server acceptance AND the actual received attachment. Later bounces/quarantine are not detectable from SMTP acceptance alone. Test-mail capture is not proof of external delivery.
